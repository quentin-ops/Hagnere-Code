# Registre maître du giga-audit — 101 guides

Date d'ouverture : **24 juillet 2026**  
Propriétaire de consolidation : **orchestrateur du giga-audit**  
Périmètre : les 101 routes `src/app/guides/*/page.tsx` recensées dans
[`inventaire-corpus.md`](inventaire-corpus.md).

Ce fichier est le tableau de bord exhaustif du chantier. Il ne valide aucun
guide par simple présence d'une ligne, d'un ancien manifeste, d'un rapport ou
d'un build. Une preuve absente, non localisable, obsolète ou rattachée à un
autre snapshot vaut **« à faire »**.

## 1. Deux vocabulaires à ne jamais confondre

### Passes du workflow

| Code   | Responsabilité           | Livrable exigé                                                                                                                                                 | Porte de sortie                                                                                           |
| ------ | ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **P1** | Recherche et décision    | benchmark France, États-Unis, Royaume-Uni et autre marché pertinent ; sources primaires ; saturation ; matrice de gain d'information ; scénarios ; plan annoté | un autre rédacteur peut écrire sans inventer, copier ou deviner                                           |
| **P2** | Rédaction et intégration | guide, registre, métadonnées, image sociale, maillage, ressource éventuelle et action autonome                                                                 | la décision du dirigeant est entièrement traitée sur un snapshot identifié                                |
| **P3** | Contre-audit indépendant | sources rouvertes, calculs refaits, concurrents rouverts, P0/P1/P2 classés, corrections revérifiées                                                            | aucun P0 ou P1 ouvert ; verdict et preuves défendables                                                    |
| **P4** | Plume humaine et QA      | relecture complète, scorecard, diff sémantique, tests, build, HTML, vrai navigateur, image sociale et statut exact                                             | au moins 90/100, aucun axe sous 8, axes critiques à 9 ou 10, aucune porte technique ou visuelle manquante |

Une passe « rapport présent » n'est pas nécessairement une passe validée.
Le rapport peut lui-même conclure `NO-GO`, porter sur un ancien snapshot ou
laisser une preuve visuelle à faire.

### Gravité des défauts

| Code       | Définition opérationnelle                                                                                                                                                   | Conséquence                                                                    |
| ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **P0**     | fait faux ou invérifiable décisif, calcul trompeur, risque juridique/sécurité majeur, comparaison qui peut conduire à une décision financière erronée, promesse inexistante | page non publiable ; corriger ou retirer avant tout autre travail              |
| **P1**     | manque bloquant de pédagogie, profondeur, preuve, comparaison, cohérence commerciale ou porte P1–P4 non franchie                                                            | page non publiable selon la charte renforcée                                   |
| **P2**     | amélioration utile mais non bloquante une fois P0/P1 fermés                                                                                                                 | planifier, corriger si le gain lecteur justifie le coût, ou rejeter avec motif |
| **REJETÉ** | suggestion examinée mais non retenue                                                                                                                                        | conserver la raison pour éviter qu'elle revienne sans nouvelle preuve          |

La mention `P1` peut donc désigner la **première passe** ou un **incident
bloquant**. Dans ce registre, les colonnes `Passe P1` à `Passe P4` parlent du
workflow ; la section « incidents » parle de gravité.

## 2. Contrat de preuve d'une ligne terminée

Une ligne ne peut recevoir `P1 validée`, `P2 validée`, `P3 validée` ou
`P4 validée` que si les éléments suivants sont tous localisables :

1. le snapshot complet contrôlé, avec SHA-256 des fichiers concernés ;
2. le dossier de recherche maintenable dans `docs/research/<slug>.md` ;
3. les URLs directes, dates, périmètres et limites des sources ;
4. la matrice de gain d'information et le critère de saturation ;
5. les scénarios et calculs reproductibles, ou la justification précise de
   leur inutilité ;
6. le rapport d'un contre-auditeur qui n'a pas rédigé le guide ;
7. la fermeture et la revalidation de chaque P0 et P1 ;
8. la scorecard justifiée et conforme au seuil de la charte ;
9. les commandes, le build et l'artefact rattachés au snapshot ;
10. le contrôle dans un vrai navigateur aux largeurs obligatoires, sans
    confondre HTTP 200, DOM, capture et inspection humaine ;
11. l'état exact : audité, réécrit, testé, publié ou indexé.

Toute modification sémantique, commerciale, structurelle ou technique après
la preuve invalide les portes qu'elle touche.

## 5. Registre exhaustif

### Légende

- `partielle` : une fiche individuelle contient une recherche concurrentielle,
  mais le dossier P1 complet et son intégration dans `docs/research/` restent à
  consolider ;
- `approfondie` : un deep-dive dédié existe ; cela ne valide pas
  automatiquement la passe P1 du snapshot courant ;
- `réécrit à vérifier` : la page a reçu une reprise liée au giga-audit, mais
  les portes suivantes ou le snapshot commun restent à établir ;
- `rapport présent` : un fichier dédié existe ; lire son verdict avant toute
  validation ;
- `à faire` : aucune preuve renforcée propre à ce chantier n'est enregistrée.

La note A/B/C/D est uniquement la ligne de base structurelle de
[`inventaire-corpus.md`](inventaire-corpus.md), pas une note de vérité ni un
score de publication.

## 7. Protocole multi-agents

Pour chaque guide :

1. l'orchestrateur attribue une mission P1 bornée à un agent ;
2. l'agent P1 ne modifie ni le guide ni les fichiers partagés et dépose son
   rapport versionné ;
3. l'orchestrateur vérifie la saturation, les sources et la matrice avant
   d'autoriser P2 ;
4. un seul éditeur applique P2 ;
5. un autre agent, au contexte froid, exécute P3 en lecture seule ;
6. l'éditeur corrige P0/P1 ; le contre-auditeur revalide les corrections ;
7. un regard distinct exécute P4 éditoriale ;
8. l'orchestrateur gèle le snapshot, lance la batterie, inspecte l'artefact et
   le vrai rendu ;
9. toute modification après le gel rouvre les contrôles touchés ;
10. le registre est mis à jour avec un lien, une date, un snapshot et un
    verdict, jamais avec une impression.

Un rapport d'agent n'est ni une source primaire, ni un test lecteur humain, ni
une preuve de publication. Aucune passe ne peut être auto-validée par son
auteur.

## 8. Mise à jour obligatoire après chaque mission

Le responsable de consolidation :

1. vérifie que le fichier annoncé existe et concerne le bon SHA-256 ;
2. relève les nouveaux P0/P1/P2 et les ajoute au registre d'incidents ;
3. remplace `en cours` par le statut réellement prouvé ;
4. laisse `à faire` pour toute porte non démontrée ;
5. consigne les suggestions rejetées avec leur motif ;
6. ne modifie pas la date publique d'un guide avant publication réelle de la
   correction ;
7. ne déclare jamais un guide « meilleur du marché », publié, indexé ou classé
   sans preuve correspondante.
